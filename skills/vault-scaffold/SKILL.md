# Obsidian vault の構築

## この skill の原則

1. **質問は1つだけ**（用途）。それ以外は全部こちらで決める。
   初心者が Obsidian をやめる最大の理由は構成が分からないことではなく、**書き始めるまでに設定が多すぎる**こと。
2. **フォルダは3〜5個まで。** 深い階層を作らない。分類はフォルダではなくリンクとタグに任せる。
3. **設定済みの状態を渡す。** プラグインの有効化、デイリーノートの保存先、テンプレートの場所まで書き込んでおく。
4. **既存のものを壊さない。** `.obsidian/` やノートが既にあるなら、足りないものだけを足す。
5. **育つ前提で作る。** 完璧な構成を最初に作らない。型が足りなくなったときの増やし方を `CLAUDE.md` に書いておく。

## 手順

### Step 0. Obsidian が起動していないか確認する

```bash
pgrep -x Obsidian
```

**起動中なら先に進まない。** Obsidian は終了時に `.obsidian/` の設定ファイルを自分の状態で上書きするため、起動中に書いた設定は消える。
「Obsidian を一度終了してください。終わったら続けます」と伝えて待つ。

### Step 1. 用途を型に当てはめる

ユーザーの答えを `references/blueprints.md` の5つの型のどれかに当てはめる。迷ったら **A（個人のセカンドブレイン）** を選ぶ。聞き返さない。

| 型 | 選ぶ目安 |
|---|---|
| A. 個人のセカンドブレイン | 「メモをためたい」「忘れないようにしたい」「日記」 |
| B. 仕事のナレッジ | 「議事録」「案件」「手順書」「顧客」 |
| C. 学習・研究 | 「勉強」「資格」「論文」「読書」 |
| D. チーム共有 | 「みんなで」「共有」「引き継ぎ」 |
| E. AI ナレッジウィキ | 「AI に読ませる」「調査」「リサーチをためる」 |

### Step 2. フォルダとノートを作る

選んだ型の定義（`references/blueprints.md`）どおりにフォルダを作り、テンプレートと最初のノートを置く。

すべての型に共通で作るもの：

| ファイル | 役割 |
|---|---|
| `00_はじめに.md` | 最初に読むノート。この vault の使い方と次の一手だけを書く |
| `CLAUDE.md` | AI がこの vault を扱うときのルール（下記 Step 4） |
| **`_ログ.md`** | **AI が何をしたかの履歴。追記のみ、新しいものが上** |
| **`_いまの文脈.md`** | **直近の状況。次のセッションが最初に読む引き継ぎ（500語以内・上書き）** |
| `Templates/` | テンプレート置き場 |
| `Attachments/` | 画像やPDFの置き場（ユーザーは触らない） |

> `_ログ.md` と `_いまの文脈.md` が**この vault を「置き場」から「育つもの」に変える部分**。
> これが無いと、AI は毎回ゼロから始まり、作業が積み上がらない。
> ただし溜めすぎると読むコストが増えるので、**1作業1行・文脈は500語以内**を守る。

### Step 3. `.obsidian/` の設定を書く

`references/obsidian-config.md` の内容をそのまま書き込む。ここが「設定済みを渡す」の実体。

- `core-plugins.json` — デイリーノート・テンプレート・Bases などを有効化
- `app.json` — 添付ファイルの保存先、リンクの自動更新
- `daily-notes.json` — 保存先フォルダとテンプレートと日付形式
- `templates.json` — テンプレートフォルダの場所
- `appearance.json` — 見た目
- `graph.json` — グラフビューをフォルダ別に色分け

### Step 4. `CLAUDE.md` を書く

この vault を AI がどう扱うかのルール。`references/claude-md-template.md` を土台に、**Step 1 で聞いた用途をそのまま目的欄に書く**。

### Step 5. 自分で検証する（ユーザーに見せる前）

**作ったものが壊れていないかを、自分で確かめてから報告する。** 生成しただけで「できました」と言わない。

```bash
# 1. JSON がすべて読める形か
for f in .obsidian/*.json; do node -e "JSON.parse(require('fs').readFileSync('$f','utf8'))" || echo "NG: $f"; done

# 2. 設定が指しているフォルダ・ファイルが実在するか
#    - app.json の newFileFolderPath
#    - daily-notes.json の folder と template（+ .md）
#    - templates.json の folder

# 3. blueprint が作ると宣言したフォルダ・テンプレートが全部あるか

# 4. .base が YAML として読めるか
```

チェック項目：

| # | 確認 | NG のとき |
|---|---|---|
| 1 | `.obsidian/*.json` が全部パースできる | 書き直す |
| 2 | `daily-notes.json` の `template` が指すファイルが実在する | テンプレートを作る。作らないなら `daily-notes.json` を消す |
| 3 | `app.json` の `newFileFolderPath` のフォルダが実在する | フォルダを作る |
| 4 | `templates.json` の `folder` が実在する | 作る |
| 5 | blueprint の宣言どおりのフォルダ・テンプレートが揃っている | 足りないものを作る |
| 6 | `.base` が YAML として読める | 最小形に戻す |
| 7 | デイリーノートを無効にした型で `daily-notes.json` を作っていない | 消す |
| 8 | `_ログ.md` と `_いまの文脈.md` がある（型E は `wiki/log.md` `wiki/hot.md`） | 作る |
| 9 | `CLAUDE.md` に「作業したら記録する」の節がある | 追記する |

**1つでも NG なら直してから報告する。** 直せないものがあれば、それを明示して報告する。

### Step 6. 結果を見せる

- ツリーで見せる
- 検証が通ったことを1行で伝える（例：「設定6件・テンプレート4件、参照先の実在まで確認済み」）
- **今すぐやること3つ**だけ伝える
- 「調整したいところはありますか？」で終わる

長い説明はしない。使い方を知りたがったら `/vault-guide` に送る。

## 既存 vault の場合

`.obsidian/` が既にある場合は**構築ではなく診断**に切り替える。

1. 現状を報告する（フォルダ数、ノート数、有効なプラグイン、テンプレートの有無）
2. 足りないものを列挙する（`CLAUDE.md` が無い／テンプレートが無い／デイリーノートの保存先が未設定 など）
3. **足すかどうかを1回だけ聞く**。既存ファイルは絶対に上書きしない

## 型を増やすとき

運用していると、既存の型に収まらないノートが出てくる。**3つ以上たまったら**新しい型を作る合図。

1. ユーザーに名前とフォルダを提案する
2. 承認されたらフォルダとテンプレートを作る
3. `CLAUDE.md` に追記する

先回りして型を増やさない。3つたまるまで待つ。

## やらないこと

- **サンプルノートを作らない。** フォルダは空で渡す。
  「田中さん」「案件A」のような架空のデータを入れると、持ち主が消す手間が増え、
  自分のノートと見分けがつかなくなる。動きを見せたいときは `examples/` の vault を使う

- MCP サーバーの設定（不要。vault 直結と公式 Obsidian CLI で足りる）
- コミュニティプラグインを6つ以上入れる（起動が3〜5秒遅くなる）
- Dataview のクエリを初期構成に含める（コア機能の **Bases** を使う）
- 深いフォルダ階層（2階層まで）
- 英語のフォルダ名（日本語話者向けの vault なら日本語で作る）
