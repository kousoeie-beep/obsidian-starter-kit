# vault の構造を設計する

**型を選ぶのではなく、用途から構造を導く。** 下の5つの型は「よくある組み合わせ」であって、
当てはまらなければ組み替えてよい。ただし**土台は全型で共通**にする。

---

## 土台：Karpathy の LLM Wiki（全型で必ず作る）

出典：[Karpathy の gist（2026-04-02）](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)。
**3層 ＋ 4サイクル**が核。この土台を崩すと、ただのフォルダ置き場に戻る。

### 3層

| 層 | 実体 | 誰が書くか | 鉄則 |
|---|---|---|---|
| **原資料** | `.raw/` | 人が置く（AI は読むだけ） | **絶対に書き換えない。** もらった PDF・議事録の録音・参考記事・スクショはここ |
| **育てる場所** | 用途別フォルダ（`02_議事録` 等） | 人と AI の両方 | 原資料を自分の言葉に直したもの。ここが資産になる |
| **運用仕様** | `CLAUDE.md` | 設計時に書く | AI がこの vault をどう扱うかのルール |

> **なぜ `.raw/` を分けるか。** 原資料と自分の解釈が混ざると、後から
> 「これは誰の意見だったか」が分からなくなる。読み返す価値が落ちる。

### 4サイクル（`CLAUDE.md` に必ず書く）

| サイクル | 何をするか |
|---|---|
| **Ingest** | `.raw/` に入ったものを読み、要約して育てる場所に1ページ作る。**原資料は変更しない** |
| **Compile** | 溜まったページを見比べ、重複をまとめ、リンクでつなぐ |
| **Query** | 質問には `_いまの文脈.md` → `index.md` → 個別ページの順に読んで答える |
| **Lint** | リンク切れ・孤立ノート・重複を点検する（`/vault-lint`） |

### 全型で必ず作るファイル

| ファイル | 役割 |
|---|---|
| `.raw/` | 原資料。immutable |
| `index.md` | 目次。何がどこにあるか。AI が更新する |
| `00_はじめに.md` | 人が最初に読むノート |
| `CLAUDE.md` | AI 向けのルール（4サイクルを含む） |
| `_ログ.md` | AI の作業履歴（追記のみ・新しいものが上） |
| `_いまの文脈.md` | 次のセッションへの引き継ぎ（上書き・500語以内） |
| `Templates/` `Attachments/` | 管理用。数字プレフィックスを付けない |

> 型E（AI ナレッジウィキ）だけは `wiki/index.md` `wiki/log.md` `wiki/hot.md` が
> この役割を兼ねるので、ルートには作らない。

## 用途から構造を導く手順

ユーザーの答えを、次の3つの軸で読む。**聞き返さずに、答えの中から読み取る。**

### 軸1：誰が使うか

| 読み取れる語 | 判断 | 構造への影響 |
|---|---|---|
| 「自分の」「個人の」「忘れないように」 | **個人** | 守秘の仕組みは不要。日記的な要素を許す |
| 「チームで」「みんなで」「共有」「引き継ぎ」 | **チーム** | **デイリーノートを無効にする**（個人の日記が混ざる）。`05_メンバー` を作る。`CLAUDE.md` に守秘レベルの運用を書く |
| 「会社の」「全社」「部門で」 | **組織** | チームに加えて `02_お知らせ`（全員が読むもの）を作る。**個人メモを置かないと明記する** |

> **kepano の指摘**：個人 vault は signal:noise を高く保つべきで、
> **AI に書かせる vault と自分の思考の vault は分けたほうがいい**。
> チーム／組織を選んだ場合は、「個人のメモはここに入れないでください」と必ず伝える。

### 軸2：何を溜めるか（複数該当してよい）

答えに出てきた語から、必要なフォルダだけを選ぶ。**使わないフォルダは作らない。**

| 出てきた語 | 作るフォルダ | 作るテンプレート |
|---|---|---|
| 会議・MTG・打ち合わせ・議事録 | `0N_議事録` | `議事録` |
| 案件・プロジェクト・仕事の進行 | `0N_案件` | `案件` |
| 手順・やり方・マニュアル・引き継ぎ | `0N_手順書` | `手順書` |
| 取引先・顧客・人・メンバー・連絡先 | `0N_人と組織`（チームなら `0N_メンバー`） | `人` |
| 勉強・資格・読書・論文・記事 | `0N_文献` ＋ `0N_まとめ` | `文献`, `まとめ` |
| 調査・リサーチ・競合・市場 | `0N_調査` | `調査` |
| アイデア・企画・構想 | `0N_アイデア` | `メモ` |
| 日記・振り返り・毎日 | `0N_日々の記録` ＋ デイリーノート有効 | `デイリーノート` |
| （何も該当しない） | `0N_ノート` | `メモ` |

**フォルダは最大5個まで。** 6個以上になりそうなら、近いものをまとめる。
迷ったら削る。後から `/vault-init` で足せる。

### 軸3：AI にどこまで書かせるか

| 読み取れる語 | 判断 |
|---|---|
| 「AI に読ませる」「調査をためる」「リサーチ」 | **型E**。`.raw/` が主役になり、`wiki/` を AI が育てる |
| それ以外 | 通常。人が書き、AI が整える |

### 組み立て方

1. 軸2で選んだフォルダに `01_受信箱` を先頭に足し、番号を振り直す（`01_` から連番）
2. 軸1がチーム／組織なら、デイリーノートを無効にする
3. 土台のファイル（上記）を全部作る
4. 選んだフォルダに対応するテンプレートだけを作る（使わないひな形を置かない）
5. 一覧表（`.base`）は、**3件以上たまりそうなフォルダ**にだけ作る

### 作った後に必ず揃えるもの（忘れやすい）

構造を組み替えたら、**それを説明している場所も全部書き換える。**
ここを飛ばすと、**作っていないフォルダが案内に出て**、持ち主が混乱する。

| 揃えるもの | 何を直すか |
|---|---|
| `00_はじめに.md` の「フォルダの意味」の表 | **実際に作ったフォルダだけ**を載せる。ひな形の表をそのまま貼らない |
| `CLAUDE.md` の「フォルダの役割」の表 | 同上。AI 自身がこの表を見て置き場を決めるので、実態とずれると誤配置する |
| `.obsidian/app.json` の `newFileFolderPath` | 実在するフォルダを指しているか |
| `.obsidian/daily-notes.json` の `folder` | デイリーを有効にした型のみ。実在するか |
| 一覧表（`.base`）の `filters` | 作ったテンプレートの `type` と一致しているか |

**Step 5 の自己検証で、この5つを必ず確認する。**

## よくある組み合わせ（出発点として使う）

以下は上の手順でよく出てくる形を先に書いたもの。**そのまま使ってもいいし、
用途がずれていれば組み替えてよい。**

---

## A. 個人のセカンドブレイン（既定）

「メモをためたい」「忘れないようにしたい」「日記を書きたい」

```
01_受信箱/          思いついたら何でもここ。整理は後
02_日々の記録/      デイリーノート（YYYY-MM-DD.md）
03_ノート/          育てるノート。受信箱から昇格したもの
Templates/
Attachments/
```

- 作るテンプレート：`デイリーノート`, `メモ`
- 作る Base：`すべてのノート.base`
- デイリーノートの保存先：`02_日々の記録`

> 受信箱を最初に置くのが要点。「どこに書けばいいか」で止まらせない。

---

## B. 仕事のナレッジ

「議事録をためたい」「案件を整理したい」「手順書を残したい」

```
01_受信箱/
02_議事録/          MTGごとに1ノート
03_案件/            案件・プロジェクトごとに1ノート
04_手順書/          やり方を書き残す
05_人と組織/        取引先・社内メンバー・会社
Templates/
Attachments/
```

- 作るテンプレート：`デイリーノート`, `議事録`, `案件`, `手順書`, `人`
- 作る Base：`議事録一覧.base`, `案件一覧.base`
- デイリーノートの保存先：`01_受信箱`

> `デイリーノート` テンプレートを**必ず一緒に作る**こと。`daily-notes.json` がこれを参照するため、
> 無いとデイリーノートを開いたときにテンプレートが当たらない。

> 議事録と人を別ノートにして `[[リンク]]` でつなぐのが Obsidian の効き所。
> 「田中さんの名前が出た議事録が全部たどれる」状態を最初から作る。

---

## C. 学習・研究

「勉強したことを残したい」「資格の勉強」「論文・読書のメモ」

```
01_受信箱/
02_日々の記録/      その日やったこと
03_文献/            本・論文・記事ごとに1ノート
04_まとめ/          自分の言葉で書き直したもの
Templates/
Attachments/
```

- 作るテンプレート：`デイリーノート`, `文献`, `まとめ`
- 作る Base：`文献一覧.base`
- デイリーノートの保存先：`02_日々の記録`

> `03_文献`（他人の言葉）と `04_まとめ`（自分の言葉）を分けるのが肝。
> 混ぜると後で「これは誰の意見だったか」が分からなくなる。

---

## D. チーム共有

「みんなで使いたい」「引き継ぎ資料」「共有の手順書」

```
01_受信箱/          行き先が決まっていないもの
02_お知らせ/        全員が読むもの
03_議事録/
04_手順書/
05_メンバー/        担当と連絡先
Templates/
Attachments/
```

- 作るテンプレート：`議事録`, `手順書`, `メンバー`
- 作る Base：`議事録一覧.base`, `手順書一覧.base`
- **デイリーノートは有効にしない**（個人の日記が共有 vault に混ざるため）。
  → `.obsidian/core-plugins.json` の `daily-notes` を `false` にし、**`daily-notes.json` は作らない**
- `CLAUDE.md` に**守秘レベルの運用**を必ず書く（下記）

> 共有 vault でも `01_受信箱` は作る。「どこに書けばいいか」で止まらせないため。
> ここが無いと、この skill と `vault-teach` の「迷ったら受信箱」という案内が成立しない。

> 共有 vault には個人のメモを置かない。同期は Obsidian Sync か Git を案内する
> （iCloud の共有フォルダは競合が起きやすいので勧めない）。

---

## E. AI ナレッジウィキ（Karpathy の LLM Wiki 型）

「AI に読ませる資料をためたい」「調査を積み上げたい」

```
.raw/               原資料。immutable（絶対に書き換えない）
wiki/
  concepts/         概念・考え方
  entities/         人・会社・製品
  sources/          原資料1つにつき要約1ページ
  index.md          目次
  hot.md            直近の文脈（500語以内）
  log.md            追記のみ。新しいものを先頭に
Templates/          concept / entity / source のひな形
Attachments/
```

- 作るテンプレート：`concept`, `entity`, `source`
- **デイリーノートは有効にしない**
  → `core-plugins.json` の `daily-notes` を `false` にし、**`daily-notes.json` は作らない**
- `CLAUDE.md` に **Ingest / Compile / Query / Lint** の4サイクルを書く

> **この型だけ他と構造が違う。** 他の型と揃える点／揃えない点を間違えないこと。
> - テンプレート置き場は他の型と同じ **`Templates/`**（`_templates/` にしない）。
>   `templates.json` は常に `Templates` を指すため、ここを変えるとテンプレート機能が効かなくなる
> - `01_受信箱` は作らない。この型では**入口が `.raw/`** になる。
>   したがって「迷ったら受信箱」の案内は**この型では使わない**。代わりに「素材は `.raw/`、
>   書いたものは `wiki/`」と伝える
> - Obsidian の画面から作業用ファイルを隠すため、`app.json` に `userIgnoreFilters` を入れる

> この型を選んだ場合、**個人の日記やプライベートなメモを同じ vault に入れない**よう伝える。
> AI が書き足す vault と、自分の思考の vault は分けたほうが、どちらの信頼性も保てる。
> （Obsidian の作者 kepano も同じ運用を勧めている）

---

## 型に迷ったとき

- 仕事の話が半分以上出てきたら **B**
- 「AI に」「調べたことを」が主目的なら **E**
- 複数人の話が出てきたら **D**
- それ以外は全部 **A**

聞き返さない。作ってから「調整するか」を聞く。
